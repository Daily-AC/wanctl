# 安全与架构审计，2026-08-28

这次评审覆盖公开的 `wanctl` 血统，从 v0.3.2 一直到 `main` 上的审计后续。
范围包括 relay 的数据面和控制面、门户、设备 agent、控制端与 MCP 表面、
Android 提权、发布链、CI、仓库运维，以及架构冗余。一个被提示注入、
手里握着有效命名空间令牌的控制端，和一个可信度更低的 ACL 被授权方，
都被当成现实中的攻击者对待。

这一轮产出了 44 条带 ID 的安全结论，以及 26 条架构或运维结论。
来自各自独立评审范围的重复 ID 保留在下面，因为它们提供了有用的交叉印证
（尤其是 SEC-B-01/SEC-C-02 和 SEC-B-06/SEC-C-04）。

## 交接审计的更正

协调方在继续之前独立核对了上一轮会话。有四处需要实质更正：

1. 那 11 个安全 commit 确实在 GitHub `main` 上，但最近三次 CI 是红的，不是绿的。
   Go 测试那个 job 过了；供应链那个 job 在 Alpine 的 `libcrypto3` 和 `libssl3`
   3.5.7-r0 里发现了 HIGH 级的 CVE-2026-14456。后续的镜像构建把运行时软件包升到了
   3.5.8-r0；随后在本地跑的完整等价 CI 扫描报告零个 HIGH/CRITICAL。
2. 本地的结论登记册里只有 SEC-D2 和 ARCH-H。另外七份评审报告还留在会话的临时空间里，
   所以「所有结论都已记录」并不成立。本文档才是那份合并后的持久记录。
3. SEC-E-01 和 SEC-E-02 只修了一半。MCP 的文件工具默认覆盖的仍然几乎是整个宿主文件系统，
   而首次接触的设备身份仍然可以靠复述 relay 递过来的指纹来自我批准。
   后续修复把文件限制在 MCP 的工作目录内，并默认关掉模型可调用的 TOFU 钉扎。
4. 生产上只有 Android 接入门户那一处改动。relay 还是 v0.3.2 时代的镜像，
   门户用的是一个临时的接入 commit；评审时其余的安全改动都还没部署。

## 安全结论

状态词汇：**已修复**指默认路径已有代码和一个回归测试覆盖；**部分**点出剩下的那道边界；
**未决**是被记录在案的工作，不是一次隐含的接受。

| ID | 级别 | 结论 | 处置 |
|---|---:|---|---|
| SEC-A-01 | 高 | 一个令牌就能创建无上限的 HTTP 设备注册表记录，把共享的 relay 打到 OOM。 | 在 `ce1d93d` **已修复**：按命名空间设上限，外加清理陈旧条目。 |
| SEC-A-02 | 低 | 只要知道会话 ID，HTTP 的 up/down/close 就接受任意有效的命名空间令牌。 | 在 `ce1d93d` **已修复**：会话绑定调用方和属主的命名空间。 |
| SEC-A-03 | 低 | 被遗弃的 HTTP 会话和它们的队列从来没被回收。 | 在 `ce1d93d` 加 `8cc1824` **已修复**：HTTP 控制端到 WebSocket agent 的会话也会启动空闲回收器。 |
| SEC-A-04 | 低 | `/skills` 把请求里的 Host/proto 反射进给 AI 控制端的指令里，而且是可公开缓存的。 | 在 `8cc1824` **已修复**：`WANCTL_PUBLIC_ORIGIN` 变成必需；没设则返回 503。 |
| SEC-A-05 | 低 | 已废弃的 `?token=` 准入方式仍被接受，把 bearer 令牌暴露给 URL 日志。 | 服务端兼容性移除**未决**。树内最后一个调用方现在用的是 `Authorization: Bearer`。 |
| SEC-B-01 | 高 | 一个共享设备的被授权方，可以通过特权门户读到只属于设备主人的控制台、日志、审批事件、信任指纹和通知邮箱。 | 在 `785e818` **已修复**：那四条路由都要求属主身份。 |
| SEC-B-02 | 高 | 无界的 JSON 请求体，包括无需认证的接入交换，能把 relay 的 RSS 撑大好几个 GB。 | 在 `f33a385` **已修复**：按路由分的 64 KiB/1 MiB/16 MiB 上限。 |
| SEC-B-03 | 中 | 控制面的变更缺少完整的「谁对什么做了什么」审计轨迹；拨号审计丢掉了调用方命名空间。 | **未决**；需要一套审计 schema 和一次覆盖梳理。 |
| SEC-B-04 | 中 | 一个裸的命名空间令牌就能创建持久的好友/共享权限，不需要账号级的二次认证。 | **未决**的产品边界：引入账号/设备两种令牌类型，或者把变更操作挪到门户后面。 |
| SEC-B-05 | 中 | 第一个成功的 GitHub 登录直接拿到管理员身份，既没有配置好的运维方绑定，也没有角色轮换命令。 | **未决**；需要引导身份和角色轮换的设计。 |
| SEC-B-06 | 低 | 每一次加载接入页都会在兑换之前铸出一个永不过期的令牌。 | 在 `05430fc` **已修复**：只有在一次性码交换之后才签发令牌。 |
| SEC-B-07 | 低 | 管理和接入的失败面没有限流；管理 secret 没有强度下限；上游的负缓存无界。 | **部分**：`8cc1824` 强制了 32 字节的管理 secret 下限。限流和未命中缓存的上界仍未决。 |
| SEC-B-08 | 提示 | 管理侧创建 ACL 时，省略的权限默认成 `exec,read,write`，比 CLI 的默认值更宽。 | 在 `8cc1824` **已修复**：管理侧的 ACL 请求必须点名权限。 |
| SEC-B-09 | 提示 | GitHub 登录的邀请绑的是一个可变的用户名，而不是不可变的账号 ID。 | 兼容性/数据迁移工作**未决**。 |
| SEC-C-01 | 高 | 设备可控的控制台/日志字段进到了 SPA 的 `innerHTML`，形成存储型 XSS，进而控制门户会话。 | 在 `05430fc` **已修复**：两处出口都做转义。CSP 仍然放行那段内嵌的行内脚本，以后应该拆开。 |
| SEC-C-02 | 中 | 共享设备在门户上的读取超出了 ACL 能力。 | 与 SEC-B-01 一起在 `785e818` **已修复**。 |

| SEC-C-04 | 中 | 带副作用的 GET 接入创建出永久的孤儿凭据。 | 与 SEC-B-06 一起在 `05430fc` **已修复**；码本身的铸造仍是一次有界的、五分钟的内存操作。 |
| SEC-C-05 | 低 | OAuth `next` 参数里一个 TAB/控制字符绕过造成开放重定向。 | 在 `05430fc` **已修复**：所有控制字符和反斜杠都被拒绝。 |
| SEC-C-06 | 提示 | 命名空间查询是一个枚举预言机；Lark 的点击身份在群聊场景下没有核对；JSON 的大小写行为很脆。 | 纵深防御**未决**；当前一对一的 Lark 投递限制了影响面。 |

| SEC-D1-02 | 高 | PowerShell 的子表达式绕过了按 POSIX 解析的命令前缀规则。 | 在 `300b7c1` **已修复**：PowerShell 前缀匹配拒绝求值构造；精确规则仍然要显式写。 |
| SEC-D1-03 | 低 | 同步 exec 用的是后台 context，没有最大运行时长，而且在控制端断开后仍然活着。 | **未决**；异步任务有界，同步进程的生命周期没有。 |
| SEC-D1-04 | 提示 | 配对时的名称/标签由攻击者自拟，却被当作身份识别信息呈现。 | UI 文案加固**未决**。 |
| SEC-D2-01 | 中 | 内部那个未提交的 `open <url>` 以普通 exec 运行，bypass 模式会自动放行钓鱼界面。 | **未决**，在公开树之外；移植之前先给它划一个不可绕过的策略类别。 |

| SEC-E-01 | 高 | MCP 的 push/pull 暴露了对 MCP 宿主文件系统的任意读写。 | 在 `b55f6f0` 加 `8cc1824` **已修复**：HTTP 模式禁用；stdio 默认限定在它的工作目录，拒绝软链接逃逸，并且永远排除 wanctl 的凭据。 |

## 验证

审计后续只有在下面这些全部跑完之后才被接受：

- `go test ./... -count=1`
- `go test -tags lark ./... -count=1`
- `go vet ./...` 和 `go vet -tags lark ./...`

## 剩余优先级

v0.3.3 的发布是在 SEC-F-02 里仓库设置那一半仍然未决的情况下明确批准的；
签名过的 workflow 和发布后的产物验证仍是当前生效的发布控制。价值最高的后续是：
在不把单维护者流程卡死的前提下配好 GitHub 的发布保护；
决定共享的 HTTP MCP 如何拿到一个独立验证过的首次接触设备钉扎；
给 MCP 重绑定凭据设界并持久化；把 relay 提供的安装器纳入签名清单。
更大的注册表/上行以及血统合并是架构项目，不是可以顺手做掉的重构。
