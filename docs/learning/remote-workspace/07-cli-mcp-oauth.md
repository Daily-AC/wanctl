# 07｜接入层：CLI、MCP 与 OAuth 怎样配合

这一篇补充实际网页测试之后的架构判断。先看三个问题，再看谁保存答案。

## 三个问题各有一个答案

| 问题 | 答案 | 生命周期由谁决定 |
|---|---|---|
| 是谁在操作、允许访问什么 | OAuth 身份及 wanctl 设备权限 | 授权服务与设备 |
| 这次工作在哪个项目、哪个 shell | 工作区引用 | 调用方保存引用，设备保存实际状态 |
| 当前请求怎么送过去 | CLI 进程、MCP 会话、网络连接 | 宿主与网络 |

OAuth 让身份跨调用、跨聊天保持稳定，这是好事。可是身份相同不代表正在做同一件事。一个人可以同时在两个聊天里开发两个项目，因此不能把“当前工作区”直接挂在 OAuth 账号上。

可以把它理解为同一张门禁卡对应多个办公室。门禁卡回答能不能进去，办公室编号回答这次要去哪里；换一辆车到楼下，不会把办公室里的桌面清空。

## CLI 怎样保存“当前在哪”

CLI 通常是一次命令启动一个进程。进程退出后，远端工作区仍然活着。调用方可以每次传引用，也可以把引用放进当前终端或 harness 的环境变量里，让它启动的子进程继承。

这一版采用环境变量 `WANCTL_WORKSPACE`，没有增加一个本地后台服务。它解决了“不同 CLI 进程持续使用同一个工作区”，也避免再维护一套连接代理、端口和后台进程生命周期。代价是短命令仍需要建立网络连接；只有真实测量显示这部分影响明显时，再考虑复用。

一个子进程不能修改父进程的环境。所以 `enter` 返回引用后，由终端或 harness 保存；`exit` 关闭远端后，由调用方清除绑定。忘记清除时，后续操作会报告工作区不可用，不会突然到另一台机器继续执行。

## MCP 怎样保存“当前在哪”

网页端采用显式工作区引用。模型从进入结果里保存引用，后续工具调用携带它。即使平台每次都重建 MCP 协议会话，设备端仍然能找到原来的 shell 和任务。

本地专属 MCP 模式可以替模型填这个参数。若宿主把工作区引用放在启动环境里，MCP 进程重启后也能继续使用。这里真正持久的是宿主保存的引用与设备保存的工作区，而不是某个 MCP 进程。

这两种接入共用同一套设备协议和权限检查。它们只是保存、传递引用的方式不同，不需要给 CLI 和网页各造一个远程执行内核。

## 相同账号还有一个边界

当前工作区归创建它的控制端身份所有。本地 CLI 与本地 stdio MCP 共用同一份身份配置时，可以交替操作同一个工作区；托管网页 MCP 的身份由服务端派生，与本地证书不同。

因此，“两边都能使用工作区”已经实现，“任意两种控制端登录同一账号就能接管对方的 shell”并未开放。这保留了原有控制端隔离。两者仍然可以按设备权限访问同一项目文件。

## 该怎样判断沉浸感

先看操作是否一直落在正确项目，目录与变量是否保留，错误后能否找到原任务，再看模型有没有频繁选错工具或补参数。不要只看工具数变少。

当前仍有明确边界：wanctl 不能自动替换宿主的原生工具；没有交互式 PTY、预览端口，也没有持久 Python 解释器。可以用 shell 调用 Python 完成复杂逻辑，但 Python 进程里的变量不会因此跨进程保存。这些是不同层的能力，需要各自有实际使用理由再做。
