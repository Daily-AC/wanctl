# 06｜从架构到交付：怎样判断第一版可用

架构描述的是责任与约束，交付需要证明这些约束在真实调用链上成立。

## 第一版范围

通用 MCP 工作区：显式打开和关闭、独立 shell、相对路径读写、执行登记和续读、网络连接结束后继续查询。使用现有的设备身份、配对和策略。第一版不把宿主自己的本地工具自动替换为远端工具。

后续独立验证：具体 harness 的 backend 切换、交互式 PTY、远端服务预览、机器重启后的恢复策略。它们不是第一版通过测试就自动成立的能力。

## 用完整任务验证

| 场景 | 可核验的结果 |
|---|---|
| 两个工作区使用同一登录身份 | 目录与环境变量互不干扰 |
| 创建、读取、编辑远端文件 | 操作同一文件，摘要检查仍有效 |
| 第一条命令设置环境，下一条读取 | 状态在同一 shell 中保留 |
| 任务运行中结束连接 | 后续能找到原任务及最终结果 |
| 重复提交相同请求编号 | 只执行一次；内容冲突被拒绝 |
| 使用其他身份访问会话 | 被拒绝 |
| 显式关闭后继续操作 | 报告已关闭，不回退其他工作区 |
| 设备不支持新协议 | 明确提示升级，不忽略工作区字段 |

## 看效率时看什么

使用同一任务、相近环境，分别记录成功完成与否、模型工具往返次数、耗时、传回内容量以及恢复故障需要几步。减少了几个参数不等于总体效率已提高。自动化测试证明行为正确，真实模型使用才证明体验和效率。

## 本轮交付状态

第一版已经在 `feat/remote-workspace-session` 分支实现，仍未合入主分支或发布到公共服务。

已实际跑通：WebSocket 和 HTTP 两种 relay 传输、设备端真实 shell 和文件操作；HTTP MCP 每次调用都新建连接会话，连续 12 个会话仍保持两个工作区独立；编译出的 `wanctl mcp` 也经过了 stdio 子进程端到端验证。

验证覆盖断线后找回原任务、重复请求不重复执行、冲突编号拒绝、同身份不同工作区隔离、不同控制端越权拒绝、文件摘要冲突、关闭后访问拒绝，以及取消、关闭与审批之间的并发。对应测试在 client、agent 和 MCP 三个位置。中文输出跨分页与分段写入也经过验证。

最终检查记录（2026-09-21，本机 macOS）：标准测试与 lark 配置各有 32 个包返回通过；两种配置的构建和 vet 均通过；新增工作区链路的 race 检测通过；Windows amd64 与 Android arm64 交叉编译通过。文档本地链接和代码围栏已检查。

交叉编译只证明能编译；没有把它当成 Windows 或 Android 真机验收。测试没有使用已部署的公共服务，也没有改变现有设备配置。

## 实际使用补充：Codex 亲自完成一次远端任务

随后，我在当前 Codex 对话中通过临时 MCP 客户端，连接真正的 Linux 测试机，开发了一个 CSV 订单汇总工具。读取需求、写代码、运行测试、定位错误、修改代码和最终验收都经由 wanctl 完成；最终 8 个测试通过。

这次使用暴露了本机测试没充分体现的问题：脚本里的环境变量没有保留，短命令也要额外建立一次连接查询结果。前者修复为在工作区自己的 shell 中执行经过验证的脚本；后者改为让设备先短暂等待命令结束。复测中状态保留正常，短命令五个样本的中位耗时从 9.94 秒变为 4.84 秒。这个数字只代表该次网络条件下的样本。

我还实际断开了 MCP 进程和网络通道，重连后找回原任务；重复提交没有重复执行。显式退出后，原工作区的读取会被拒绝。

这说明“能连续干活”已经有实际任务证据。第一轮仍有数秒等待，并且需要携带工作区标识；[第一轮使用记录](../../plans/2026-09-21-workspace-immersion.md)保留了当时的观察。

## 第二轮：自动绑定与连接复用

随后实现了一个进程专属一个对话的 MCP 模式。我用两个独立进程，在真实 Linux 机器上继续修改订单工具，新增口味筛选，最终 12 个测试通过。22 次成功的读写、执行和查询操作中，没有一次需要填写设备或工作区参数；设备日志记录了 5 次连接，其余操作复用了已有通道。

这轮 7 个短执行样本的中位耗时为 0.591 秒，范围是 0.075 到 2.131 秒。初次进入仍约 4.8 秒。网络条件会变化，因此这些是实际样本，不是所有部署都能达到的性能承诺。

两个会话的目录与环境保持独立；断网后原会话直接找回任务；MCP 进程重启后，通过重新附着恢复原 shell；退出 A 后 A 拒绝继续执行，B 仍能工作。这次已证明专属 MCP 工具链里的自动绑定有效。[第二轮完整记录](../../plans/2026-09-22-workspace-conversation-trial.md)列出了证据与边界。

还没有验证：真实网页 AI 的持续使用、宿主原生工具自动接管、交互式终端与端口预览。现有公共 MCP 连接不会自动获得分支上的新功能。

需要复现时，另看[开发版使用与验证说明](../../workspaces.md)。日常学习仍按本系列的宏观顺序阅读即可。

## 如何继续理解源码

源码阅读可以留到需要解释某一个行为时：协议负责表达请求，client 负责发送，agent 负责权限和执行，MCP 负责把调用方参数变成请求。先沿一次真实调用横向走完，再深入某一个组件，仍然保持 BFS 的顺序。
