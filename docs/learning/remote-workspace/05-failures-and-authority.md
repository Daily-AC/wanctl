# 05｜故障与权限：断网时为什么不能猜

前几篇描述正常流程。这一篇看同一套组件如何面对故障和拒绝，不引入另一套系统。

## 最危险的误判：没收到结果等于没执行

假设命令已经创建文件，结果返回时网络断了。调用方只知道没有收到结果，不知道文件是否创建成功。如果立即重发，就可能执行第二次。

因此每条命令带一个请求编号。设备端保存该编号对应的命令和执行状态。重连时查询原编号；再次提交同一编号和同一内容，只返回原任务。同一编号却带不同内容必须拒绝。

这保证的是设备进程存活、执行记录仍保留期间不重复启动。它不等于跨机器重启的“恰好执行一次”。记录已丢失时，应报告未知或失效，而不是替调用方猜测。

## 三种停止

| 情况 | 应当发生的事 |
|---|---|
| 调用方不再等待结果 | 保持已受理任务，允许之后查询 |
| 用户明确取消 | 停止任务，准确报告停止结果及 shell 是否丢失 |
| 用户退出工作区 | 关闭工作区，不再接受其中的新任务 |

取消一条 shell 命令并同时保留所有 shell 状态并不总能保证。第一版可以明确让取消结束该 shell，并让工作区报告失效；不能把残余状态当成完好状态继续使用。

## 一套授权，多个对象

工作区标识用于定位，身份用于证明调用者。每次访问仍然验证设备授权与会话归属，执行和文件操作仍经过原来的 wanctl 策略。不能把“进入过工作区”当成无限期授权。

权限到期、撤销与网络断开不同。持久工作需要明确的授权生命周期。第一版不把现有的短期委托权限自动扩展成持久会话；不支持的授权形态应明确拒绝。

## 根目录不是自动沙箱

根目录帮助解释相对路径，不代表任意 shell 命令都被限制在其中。允许执行程序的能力仍是设备原有的执行授权。若要限制程序的系统调用、网络或整个文件系统，那是操作系统隔离的一层，不能靠路径前缀或 Python 包装来承诺。

## 有界资源

设备需要限制工作区数、保留的执行记录和输出大小，并在达到限制时说清楚。保留记录期间可以准确去重；记录不能为了省内存被悄悄删除后允许相同编号再次执行。
