# 04｜流程：进入、干活、查看、退出

现在已经知道组件和状态，这一篇横向看四条主流程。例子始终是让 AI 修改远端项目并运行测试。

## 进入

调用方选择设备和项目目录。设备身份、控制端身份及访问权限按 wanctl 现有机制确认。设备端检查目录，建立独立工作区，返回标识和项目根目录。调用方保存它；如果宿主支持工作区后端，也在此时记录原来的本地环境。

进入并不是批准接下来的一切操作。后续读写和执行仍经过设备策略。项目里的 AGENTS.md 或 CLAUDE.md 应在正式工作前读取。

## 文件操作

文件请求带工作区标识和路径。设备端在项目根目录下解析相对路径，然后执行现有的权限检查、读取或原子修改。文件版本摘要仍然用于发现并发修改。

工作区根目录与终端当前目录是两个概念。根目录决定项目身份；终端可以 cd 到子目录。建议文件工具始终按项目根目录理解相对路径，这样一个终端切目录不会改变另一个文件请求的含义。

这也是为什么不需要先把整个项目复制到本机。读写可以直接发生在远端真实文件上，避免出现本地副本与远端运行版本不一致的问题。

## 执行与查看结果

设备端接收命令，为它登记请求编号，再交给工作区 shell。短命令可以很快返回结果；长命令返回运行状态，后续用相同编号续读输出。一个持久 shell 同时处理一条命令，忙时明确报告，不偷偷开另一个丢失状态的 shell。

输出需要同时包含“内容”和“状态”。空输出不表示成功，也不表示没有运行。只有任务结束后，退出码才有最终意义。

## 退出

显式退出关闭远端工作区及它管理的 shell，调用方停止将新操作发往该工作区。若宿主保存了原来的本地 backend，此时恢复；通用 MCP 只结束自己的远端工作区，不会修改另一个本地工具的状态。

## 可见产物

命令输出和文件内容是第一版主要反馈。远端网页服务的预览还需要端口映射；图片和构建产物需要对应的读取和展示入口。这些同属工作区体验，但应该各自验证，不能因为命令跑通就宣称所有界面都已接通。
