# wanctl v0.1.6

This release makes a reinstalled device recoverable. Reinstalling one — or just
clearing its credentials — could put it in a state where the portal listed it as
**online** and no action available in any UI could reach it again. Found in
production on 2026-08-06; the reasoning is recorded in
`docs/adr/0002-device-identity-trust-is-acknowledgeable.md`.

## Fixes

- Give a changed device identity somewhere to be acknowledged. The portal pins
  each device fingerprint on first console dial, seeded from the relay's own
  `/admin/devices` record — which makes it a change alarm, not an
  authentication. The alarm had no acknowledge path. A mismatch surfaced as a
  bare 502 whose body the SPA discards, so the browser said "连不上这台设备，可能
  它不在线" and never displayed either fingerprint; and unbinding the device
  deleted only the relay-side record, leaving the pin on the portal's persistent
  volume to reject the same device name forever. A mismatch now returns 409 with
  both fingerprints and the portal renders an approval card. Accepting is
  owner-only and must echo the fingerprint the browser displayed, so a stale tab
  cannot pin whatever is claimed later, and neither the device nor the relay
  speaking for it can clear its own alarm. Unbinding now forgets the pin, scoped
  by name — `Store.Remove` deletes every entry sharing a fingerprint, and one
  machine is routinely pinned under several names.
- Seed the portal's console-admin identity at enrollment. A device accepts the
  portal's web console only if the portal fingerprint is in its
  `portal_admins.json`, and the agent fails closed on an empty set. Nothing
  wrote that file: not the installer, not enroll — only a hand-passed
  `--portal-fps`, which v0.1.5 made possible for services but still required
  someone to remember. Every install was therefore invisible to the portal
  console until someone did, and clearing a device's config silently undid it.
  The portal now declares its fingerprint when minting an enrollment code, the
  relay carries it on the code, and the device trusts it on completing
  enrollment.
- Show the approval card's `影响 impact` line. `.fact .v.warn` inherited
  `display: none` from the global `.warn` banner rule, so the field stating what
  a pending operation would do has never been visible in any release.

## Security notes

The portal fingerprint reaches the device through the relay, so a compromised
relay could nominate itself console administrator on devices enrolling from now
on — a capability it does not have when the value is passed by hand. The
exposure is bounded deliberately: it is seeded only at enrollment, so an
already-enrolled device never gains a console administrator from the wire; the
terminal prints the fingerprint it trusted and the enroll page shows the same
value, and that page is the one leg of the handoff the relay is not on;
`--portal-fps` and `WANCTL_PORTAL_FPS` still take precedence. The trade-off and
the rejected alternatives are in ADR 0002.

## Compatibility

`portal_fp` is optional in both directions of the enrollment exchange, so any
mix of old and new relay, portal and client enrolls devices exactly as before.
`client.ExchangeCode` now returns a `client.Enrollment` instead of three values.

## Upgrading

Devices enrolled before this release are not back-filled — they still need a
one-time `wanctl portal-admins add <portal-fp>`, run as the account whose config
directory the agent uses, or a restart with `--portal-fps`. Re-enrolling on
v0.1.6 does it automatically.

A device already stranded by a stale pin is recovered from the portal: open it
and accept the new identity, or unbind it and re-run `wanctl`.

## Also

The portal's mascot no longer carries its own near-white backdrop, so the header
lockup and the loading screen stop showing a pale card on the cream page, and
the enroll page's shield emoji is now an inline SVG.
