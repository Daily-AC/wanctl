# wanctl v0.1.13

One feature, and it is the one that decides whether an Android phone is a real
controlled device or a demo: `wanctl exec` can now do what `adb shell` can do.

Everything before this release ran inside the app sandbox. `pm`, `am`, `input`,
`screencap`, `dumpsys`, `settings`, `wm`, `svc` — the useful half of Android —
were unreachable, and not for want of a feature. `adb shell` is uid 2000 in the
`shell` SELinux domain; the agent is an ordinary app uid in `untrusted_app`.
v0.1.12's `battery` verb had to collect its value through Java precisely because
of this, and that approach does not generalise: most of adb's surface has no
app-visible equivalent at any price.

So this release does not add verbs. It adds **one elevation channel**, after
which the whole surface follows.

## `--elevate`

```sh
wanctl exec --target phone --elevate -- pm list packages -3
wanctl exec --target phone --elevate --via su -- dumpsys battery
```

Two channels, probed in order, first available one wins:

| channel | needs | survives a reboot |
|---|---|---|
| `su` | a rooted device | **yes** |
| `adb` | Developer options → Wireless debugging | no — Android clears it on boot |

`--via` pins one, and pinning an unavailable channel is an **error rather than a
downgrade**. A command that ran unprivileged after you asked for root is a wrong
answer wearing a right answer's clothes.

Only `su` keeps working with nobody touching the device. A phone that must stay
controllable unattended after a power cut should be rooted, or should not depend
on elevation. That is a platform fact, not something wanctl can engineer around,
and it is said here rather than discovered later.

## The adb channel: no root, no cable, no second app

On an unrooted phone the agent becomes an adb client and connects to its own
adbd over loopback. Turn on **无线调试**, then pair once:

```sh
wanctl exec --target phone -- adb-pair 41439 891268
```

The port and the six digits come from 设置 → 开发者选项 → 无线调试 → 使用配对码
配对设备. That screen shows two ports and they are different listeners; use the
one next to the code. The verb runs **on the device**, because only the device
can reach the pairing port its own adbd opened, and it needs no elevation —
requiring elevation to set up the elevation channel would be a loop with no
entry point.

Pairing is Android 11+'s SPAKE2 exchange, implemented here from scratch:
BoringSSL's variant over Ed25519, which is not RFC 9382 and which no Go library
implements. It interoperates with the real thing — the device's own 已配对的设备
list shows `wanctl@<device>`, which is the strongest evidence available.

The key lands in `/data/misc/adb/adb_keys` and survives reboots. Wireless
debugging does not, so after a restart the switch has to be flipped again — but
the code does not have to be typed again.

**The port is discovered, not configured.** Android picks a new one every time
wireless debugging is enabled and publishes it only over mDNS; measured on one
device, it moved from 37819 to 41031 across a single re-pair. The app watches
`_adb-tls-connect._tcp` and hands what it finds to the agent. Only its own
device's advertisement counts — every phone on the same Wi-Fi with wireless
debugging on publishes that service, so the resolved address is checked against
this device's own addresses before the port is believed.

## Elevated commands are their own class

**`bypass` mode does not cover them.** The 自动放行所有命令 switch exists so an
unattended device is usable at all; it must not also be the thing that hands out
uid 0 without anyone deciding to. An elevated command on a bypass-mode device
still needs an explicit rule or a human approval in the portal, and an `exec`
rule never authorises the elevated form of the same command.

The APK gets its own switch, **提权通道**, off by default and off after an
upgrade — no device becomes more powerful because someone installed a new
version. With it off the channels are not probed and the port is not watched: a
rooted phone raises no root-manager dialog, and a phone whose owner has not
enabled this is not listening for the port that would enable it.

Every elevated command is written to the event log with the channel that ran it,
so `wanctl logs` can answer *what has run as root on this phone*.

## Verbs

Shorthand for the parts of the adb surface that are awkward over a pipe. Each is
one shell command through the same channel, gated by the same policy class,
recorded in the same log.

```sh
wanctl screenshot phone -o shot.png       # implies --elevate; "-o -" writes stdout
wanctl exec --target phone --elevate -- input tap 540 1200
wanctl exec --target phone --elevate -- app list -3
wanctl exec --target phone --elevate -- settings get global adb_wifi_enabled
wanctl exec --target phone --elevate -- prop get ro.build.version.release
wanctl exec --target phone --elevate -- logcat -f
```

## Measured, not assumed

Every claim above was checked on hardware.

On a **Xiaomi Mi 10 Ultra** (Android 11, Magisk), over a live relay: plain exec
returns `uid=2000`, `--elevate` returns `uid=0 context=u:r:magisk:s0`,
`screenshot` returns a real PNG, the event log names the channel.

On an **OPPO Reno8 / PGBM10** (Android 14, **not rooted**, no cable), through
the APK with no port configured anywhere:

```
exec            → uid=10606(u0_a606) … context=u:r:untrusted_app:s0:c94,…
exec --elevate  → uid=2000(shell)    … context=u:r:shell:s0
```

Same agent process, same command, two channels. `pm list users` works, exit code
42 survives the round trip, `screenshot` returns a real 1080×2400 PNG, and it
reconnects after the agent restarts without re-pairing.

That last measurement answers a question this work carried from the start, and
the answer was not obvious: an OEM ROM (ColorOS 14) **does** let an app uid reach
its own adbd over loopback.

## One thing that costs a human, once

The first time an agent connects to an adbd it has not paired with, the device
raises **允许 USB 调试吗？** showing wanctl's key fingerprint, and it says so
rather than timing out. That prompt cannot be answered from software: `input tap`
against it fails with `SecurityException: Injecting to another application
requires INJECT_EVENTS permission`, which is the platform working as designed —
if a program could tap that button, any program could grant itself shell access.

Plan an unattended rollout knowing that.

## Shizuku is not a channel

It was planned as a third one and dropped before release. It reaches the same
uid 2000 in the same domain the `adb` channel already reaches, and on an
unrooted phone Shizuku is itself started by wireless debugging — so it cannot be
the fallback for a device that lacks wireless debugging; it is wireless
debugging plus an app to install, update and restart. `--via shizuku` says it was
dropped rather than reporting an unknown channel.

## Also in this release

**Built on Go 1.26.6.** The previous toolchain carried six standard-library
advisories and, in the container image, CVE-2026-46600 — a denial of service in
the DNS message parser, fixed in no 1.25.x. The release binaries and the image
are built on the fixed toolchain rather than on an ignore list.

## Upgrading

The wire protocol gains two optional fields. A controller that does not ask for
elevation is byte-identical to before, so **controllers and agents upgrade
independently and in any order**.

Asking an *older* agent to elevate is the one case worth knowing: it ignores the
unknown field and runs the command unelevated. The controller detects the reply
that echoes no channel, reports it as a failure, and says the command has
already run — which is the honest thing to say and the reason not to retry it
blindly.

Elevation itself needs the new APK on the phone, plus the 提权通道 switch, plus
either root or a pairing. Nothing turns on by itself.
