# wanctl v0.1.11

Android gets a real app. The agent now ships as an installable APK that carries
the wanctl binary inside it, runs under a foreground service, and comes back
after a reboot — which the Termux route never did.

Other platforms are unchanged apart from two things that apply everywhere: a
diagnostic improvement to the HTTP transport, and `wanctl update` no longer
deleting files it had not identified.

**Deploy note:** the production relay had been serving v0.1.7 since 2026-08-06 —
v0.1.9 was released but never deployed. Anyone who installed from `/dl` in that
window has the build whose `wanctl update` targets the system dynamic linker.
Deploying this release replaces it.

**On the version number:** this content was tagged `v0.1.10` first. That tag
cannot build the APK — `.gitignore`'s bare `wanctl` pattern had kept the app's
Java sources out of the repository entirely — so it was withdrawn unpublished
and the number burned. See `v0.1.10.md`.

## The Android app

Install `wanctl-android-arm64.apk`, open it, tap 登录, turn on the switch. No
terminal emulator, no shell, no `PATH`.

The binary ships as `lib/arm64-v8a/libwanctl.so` with
`android:extractNativeLibs="true"`. That is not a disguise for a shared library:
an APK's `lib/<abi>/` directory is the only place an ordinary Android app may
execute from, because it is labelled `apk_data_file` while everything the app
can write is `app_data_file`, and the package manager only materialises it on
disk — with the executable bit — for files named `lib*.so`. Termux ships its own
bootstrap the same way. Full reasoning in `docs/adr/0003-android-apk.md`.

**All four Termux workarounds cease to apply**, because nothing intercepts this
process's execs: `argv` arrives intact, `os.Executable()` answers correctly, the
binary can exec itself, and `/system/bin/getprop` is reached by absolute path.

The app carries a foreground service (type `specialUse`, not `dataSync`, whose
six-hour daily cap on API 35 would be fatal for an always-on agent), a
`BOOT_COMPLETED` receiver, a persisted 15-minute reconciler job, a partial wake
lock, and switches for autostart, auto-trust and policy bypass.

## `wanctl update` cannot work on Android any more

The only directory the app may execute from belongs to the package manager and
is read-only, so the unit of update is the APK. `wanctl update` now detects that
it is running from one and says so, instead of falling through to the sudo path
and reporting that it cannot find `sudo`.

Updates come from the app's 检查更新 button. The binary fetches the signed
release manifest, verifies its Ed25519 signature and the APK's SHA-256 against
the key compiled into it, and hands the verified file to the system package
installer — which then checks the APK signature against the installed app's. Two
independent signatures have to agree.

The APK rides in the **existing** signed manifest as platform
`android`/`arm64.apk`. The schema is untouched on purpose: `VerifyManifest`
rejects a schema it does not know, and that check runs inside `wanctl update`
before it can update itself, so bumping it would strand every already-installed
client on every platform. Verified by pointing a real v0.1.6 binary at a
manifest carrying the new entry: it parsed, verified, and updated itself.

## The relay poll loop now reports failures

Every error in the agent's HTTP poll loop used to be swallowed — sleep two
seconds, retry, say nothing. An agent whose polls had stopped working therefore
looked identical to a healthy one from the device (process alive, no errors,
"online" printed once at startup and never contradicted) while having vanished
from the controller's `wanctl peers`. It now logs the first failure, then about
one a minute, then the recovery. Applies to every platform.

## New

- `wanctl login --code CODE` — non-interactive enrollment for a front-end that
  ran the browser step itself. The Android app uses it; so can a script.
- `wanctl update --fetch-apk DIR` — download and verify the Android APK, print
  its path, exit. Used by the app; usable anywhere for checking what a release
  offers.
- `scripts/build-apk.sh` — builds and signs the APK with the Android SDK's own
  tools. No Gradle, no AndroidX, no network.

## Fixed

- **`wanctl update` deleted files it had not identified, as root.**
  `pruneStaleCopies` removed every file named `wanctl` on `$PATH` other than the
  one being updated, testing nothing but the basename — so a wrapper script that
  sets `WANCTL_RELAY`, a developer's own build, or a packaged `/usr/bin/wanctl`
  went without ever being read. Its comment argued the blast radius was bounded
  by permission denied, but the root-owned-directory case re-execs the command
  as `sudo wanctl update --no-restart`, and that child ran the prune as root
  with root's `$PATH`, where nothing denies it. It now answers the narrower
  question that motivated it — after the swap, does typing `wanctl` run the copy
  we just replaced? — with `exec.LookPath` and `os.SameFile`, and prints the
  shadowing path plus the command that identifies it. Nothing is removed.
- `docs/android.md` told people to install from `/dl/install.sh`, which 404s —
  `/dl` serves only what the signed manifest names. The correct URL is
  `/install.sh`. The documented Termux one-liner had never worked.

## Verified

On a vivo PA2353 (Android 13) against the production relay, driving it from a
Mac, using the installed APK and its own UI rather than adb shortcuts:
enrollment through the app; `exec` with streamed output and a real exit code;
512 KB `push`/`pull` byte-identical; **two reboots with the screen asleep and
nobody touching the device, still controllable**; eight minutes of screen-off
still online; `update --fetch-apk` downloading and verifying a signed APK.

Handing the verified APK to the system installer has **not** been exercised —
no published release has carried the artifact yet. This one will.

## Known limits

- **A Chinese OEM ROM will freeze the app** unless told not to, and neither a
  foreground service, nor a wake lock, nor the AOSP battery-optimisation
  exemption prevents it. On the test device the processes landed in
  `freezer:/frozen` about two minutes after screen-off. The gate is a separate
  vendor setting (vivo: 设置 → 电池 → 后台耗电管理 → 允许后台高耗电). The app's
  battery dialog names the path for vivo, OPPO, Xiaomi and Huawei.
  `docs/android.md` has the measurements.
- **`BOOT_COMPLETED` is best-effort.** One reboot in four was discarded by the
  system while other apps received it in the same second. The persisted job is
  the floor under that; worst case the agent is a quarter of an hour late.
- File transfers must target the app's own directory. An app UID cannot write
  `/data/local/tmp`.
