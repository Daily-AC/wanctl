# wanctl v0.1.5

This patch release fixes three failures that were silent, one of which filed a
false report in the audit log, and adds a user-facing changelog to the portal.

## Fixes

- Rebind the approver when the policy mode changes at runtime. `Agent.New` chose
  the approver once, from the startup `--mode`, so an agent started with
  `--mode bypass` held an `AllowApprover` for its whole life. Turning bypass off
  from the portal changed `engine.Mode()` and both gates stopped
  short-circuiting on it, but the approver they then consulted still allowed
  everything — and the audit log recorded those requests as `approved`, the
  decision string that means a human said yes. The log therefore asserted human
  review of commands nobody ever saw, which is worse than recording `bypass`.
  Bypass is a property of the engine and both gates already check it first, so
  the construction-time branch was redundant as well as wrong.
- Carry the device name and the portal admin fingerprint into the service unit.
  `wanctl service install` emitted `agent --managed` and nothing else, and a
  unit is what runs after a reboot with nobody at a terminal to supply the rest:
  the device name silently degraded to the hostname, and the device came up
  trusting no portal admin at all. That second one has no local symptom — the
  agent refuses the portal's console session and whoever clicks "trust" in the
  browser gets a bare 502. `install.sh` does not inject the fingerprint either
  (`DefaultPortalFP` is an empty compatibility constant), so every freshly
  installed device started out in that state. `service install` now accepts
  `--name`, `--portal-fps` and `--mode` and bakes them into the systemd unit,
  the launchd plist and the Scheduled Task. `--mode` is opt-in: baking one in
  makes the unit outrank the persisted mode, undoing a portal-side switch on the
  next restart. With no fingerprint configured and none supplied, installation
  now states the consequence up front.
- Give the Lark approval card an absolute portal link. `deviceURL` fell back to
  a relative path when `PORTAL_PUBLIC_ORIGIN` is unset, which the deployed
  portal does not set because that variable only matters when TLS terminates
  upstream. A card renders inside a Lark client, which has no origin to resolve
  a path against, so the "open in portal" button did nothing on every card ever
  sent.

## Features

- The portal has a 更新日志 tab and a version badge in the header. The release
  notes it shows are Chinese and user-facing — what changed and whether it
  affects you — and are embedded in the binary rather than stored in the docs
  table, so the page always describes the version actually deployed. The
  English notes in `docs/releases` remain the engineering record.

## Upgrade note

An agent started with `--mode bypass` before this release is auto-allowing every
request regardless of what the portal shows, so upgrade and restart it. Past
audit entries can be told apart: a genuinely approved request is always preceded
by a `remote decision … by …` entry, and an `approved` without one came from
this bug.
