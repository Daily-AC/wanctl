# wanctl v0.1.4

This patch release fixes three things that reported success while failing:
installation from the relay, upgrades of a supervised agent, and rejected
sessions.

## Fixes

- Serve `manifest.json.rsa.sig` from the relay. Both installers fetch it right
  after the manifest, and the signed-distribution handler served only the
  manifest, its Ed25519 signature, and the artifacts the manifest names — so the
  one-line install in v0.1.3 aborted with a 404 on every platform before
  downloading anything. Nothing about the published v0.1.3 artifacts was wrong;
  the relay simply would not hand out one of them.
- Stop reporting an upgrade that did not happen. When a supervisor runs the
  agent under another account — a Windows Scheduled Task as SYSTEM, a systemd
  unit as root — a user-run `wanctl update` cannot terminate it, and the
  termination happens in a detached helper whose failure went unreported.
  `wanctl update` replaced the binary, printed success, and left the old process
  serving. It now refuses up front when it cannot signal the agent, naming the
  service to restart with elevation, and otherwise confirms that a different
  live agent took over before claiming success. `wanctl status` says when the
  agent is owned by another account, before an upgrade is attempted.
- Report a process owned by another account as running, on Unix. The liveness
  probe treated the `EPERM` from `kill(pid, 0)` as "not running", so
  `wanctl status` denied that a root-owned agent existed and `wanctl stop`
  claimed the same while deleting its pid file. Both now report the real
  permission error instead.
- Deliver a session rejection before closing the connection. The relay tears
  both directions down as soon as either ends, so a device that closed
  immediately after writing its rejection could race those bytes away — the
  controller then saw EOF instead of the reason, losing "capability denied" or
  the pairing URL a user needs to visit to approve a new controller.

## Upgrade note

The updater fix cannot fix the updater that runs it. Upgrading from v0.1.3 uses
v0.1.3's updater, so if a supervisor owns your agent under another account, that
upgrade will still report success without restarting it — check with
`wanctl status` that the pid changed, and restart the service with elevation if
it did not. Upgrades from v0.1.4 onward report the truth.

## Install

```sh
curl -fsSL https://relay.example.com/install.sh | sh
```

```powershell
irm https://relay.example.com/install.ps1 | iex
```

The strongest bootstrap is to download `install.sh` or `install.ps1` from this
GitHub release rather than from the relay: a compromised relay could serve a
matching script and public key. See `docs/release-signing.md`.

Public release: <https://github.com/OWNER/wanctl/releases/tag/v0.1.4>

No OpenSSL installation is required on any supported platform.

## Compatibility

- Linux: amd64, arm64
- macOS: amd64, arm64
- Windows: amd64

Production uses `https://relay.example.com` with HTTP long-poll.
