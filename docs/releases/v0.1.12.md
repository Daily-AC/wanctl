# wanctl v0.1.12

Usability and diagnosability, all of it found by trying to answer one ordinary
question — "how much has my phone charged?" — and failing.

That question could not be answered at all: the Android agent runs as an
`untrusted_app`, where every shell route to battery state is closed. Getting to
an answer surfaced six more problems, each of which failed in the same
direction: **silently, while looking like it worked.** That is the theme of this
release.

## Android can answer for itself

`wanctl exec -target <phone> -- battery` returns level, charge status, plug
source, temperature and health as JSON.

The shell could never have done this. Measured on a real device, the agent lives
in the most restricted SELinux domain Android has:

```
uid=10601(u0_a601) context=u:r:untrusted_app:s0:c89,c258,c512,c768
```

`/sys/class/power_supply` is denied (even listing the directory), `dumpsys
battery` cannot reach servicemanager, there is no Termux and no `su`, and
`getprop` carries no level — only `debug.tracing.battery_status`, which is
refreshed solely while the atrace battery tag is on and is therefore not
trustworthy. The state exists only behind a Java API, so the app now collects
`ACTION_BATTERY_CHANGED` into `files/state/device.json` (atomic rename) and the
Go side answers the verb from that file.

**Staleness is reported, never papered over.** A missing file, a corrupt one, an
impossible timestamp, or an age over 10 minutes all produce an explicit
"unavailable" naming the reason. A stale battery level dressed up as current
would be worse than no answer.

This is the first of a batch. `netinfo`, `deviceinfo` and `screen` follow the
same pattern and are not in this release.

## `exec` stops mis-reading your command

**The device name works where you'd expect it.** `wanctl exec my-phone whoami`
now targets that device. Previously only `-target` was honoured and every
positional argument was joined into the command — so with several devices online
you got an error that helpfully listed the name you had just typed, and with a
single device online it silently ran `my-phone whoami` **as a command on that
device**. An explicit `-target` still disables the inference, which is the escape
hatch if a command ever collides with a device name.

**Lost quoting now warns.** Your local shell strips the quotes from
`sh -c '<script>'` before wanctl ever sees them, so the device receives loose
words and runs only the first one. Three real cases from one debugging session:

| Typed | Actually ran | Symptom |
|---|---|---|
| `sh -c 'ls -d /some/path; command -v pkg'` | `ls` | printed the **cwd listing** — read as "the path exists" |
| `sh -c 'for p in a b c; do echo $p; done'` | `sh -c for`, rest in the outer shell | syntax error |
| `sh -c 'echo x; cat a; cat b'` | a bare `cat` read stdin | hung until timeout |

The first is the dangerous one: no error, plausible output, wrong conclusion.
wanctl now says so and points at `-script <file.sh>`, which is sent
base64-encoded and cannot be re-split. `-script` also explains itself when handed
a command string instead of a path.

## `status` stops describing the wrong machine

`wanctl status -target <device>` reports the remote agent — running state, policy
mode, agent version. Previously `status` ignored every argument it was given, so
`wanctl status --target phone` cheerfully printed the **local** agent's state and
nothing said so. Unknown flags and stray arguments are now errors, and the local
output says it is local. Agents too old for the new verb degrade to "online, but
cannot report mode/version" instead of failing.

## Server logs without a browser

`wanctl logs --service portal|relay [--since 30m] [--grep lark] [--limit 500]`,
plus an MCP tool (`wanctl_server_logs`) and a secret-gated `GET /admin/logs`.

Both roles tee their output into a bounded in-process ring buffer (2000 lines or
2 MiB, whichever comes first; cleared on restart — diagnostics, not an audit
trail). Redaction runs **before** grep, so the filter cannot be used as an oracle
for token-shaped values.

This existed because debugging the control plane meant leaving the tool: opening
a browser, logging into the hosting console, and reading a log pane by hand.

## Feishu approvals stop failing silently

Two fixes to the same blind spot.

**Delivery health is visible.** Every device now carries the last delivery
attempt — timestamp, outcome, kind (`dial`/`approval`/`pairing`), error text and
consecutive-failure count — on the portal device page and in the JSON APIs. Both
failure paths used to `logf` and continue, so a switch reading "on" while
delivery was completely broken looked exactly like a switch that was off. A
successful reconnect clears only a *dial* failure; it must not make a failed card
delivery look healthy before another card is actually sent.

The device's policy mode is now shown next to the switch too, because a device in
`bypass` produces no approval pendings at all — the switch is decorative there
and nothing used to say so.

**A dead device no longer floods the log.** A watcher whose device is not
registered with the relay used to retry on the ceiling backoff forever. In
production one device reached **dial attempt 17700** — one line every five
minutes for months — and its noise pushed every other portal event out of the
log, which is what made an unrelated Feishu failure impossible to diagnose.
Permanent dial errors are now typed (classified via `errors.As`, not string
matching, so a transient blip cannot be mistaken for one), stop the watcher, and
record why. Recovery is event-driven: a config change or the device registering
brings it back. Log throttling is per device per hour, and the first failure is
still reported immediately.

## Upgrading

Nothing in this release changes the wire protocol or on-device state, so
controllers and agents can be upgraded independently and in any order. The
`battery` verb needs the new APK on the phone; everything else is controller- or
server-side.
