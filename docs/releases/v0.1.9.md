# wanctl v0.1.9

Makes Android support in Termux actually work. v0.1.7 shipped it broken, and
v0.1.8 fixed only the first of four problems (see `v0.1.8.md` — it was withdrawn
rather than published).

Everything here is Android-only; other platforms are unchanged in behaviour.
Devices installed over `adb` were never affected by any of it, because nothing
intercepts exec there.

## Why Termux breaks what adb does not

Two Android rules combine badly, and they were hit one at a time:

1. Go's Android target is always dynamic PIE, so Termux's exec interceptor runs
   wanctl through the dynamic linker and **prepends the program's absolute path
   to `argv`**.
2. Android refuses `exec` of any file inside an app's private data directory
   from the `untrusted_app` domain. Termux only runs its own binaries by going
   through the linker; a CGO-free Go binary, which loads no interception
   library, simply cannot.

## Fixes

- **A bare command name was still shifted.** v0.1.7's duplicate detection needed
  `argv[0]` to resolve as a file, true for `./wanctl` and for an absolute path
  but not for `wanctl` off `PATH` — which is what one types after installing. So
  the installed binary answered everything with
  `unknown command "/data/data/com.termux/files/usr/bin/wanctl"`. The marker is
  now that `argv[1]` is an absolute path to a regular executable whose base name
  matches `argv[0]`'s, covering all three forms.

- **`wanctl update` aimed at the dynamic linker.** `os.Executable()` reads
  `/proc/self/exe`, which under Termux *is* the linker. Update replaces the path
  it is given, so **on a rooted device this would have overwritten
  `/apex/com.android.runtime/bin/linker64` and taken the Android runtime down
  with it**. Unrooted it failed with a permission error naming linker64, which
  is how it was found. The binary's real path — which Termux hands over as the
  duplicated `argv[0]` — is now used instead. This affects v0.1.7 as well:
  **do not run `wanctl update` as root on a v0.1.7 Termux install.**

- **`wanctl start` could not launch its own binary**, failing with
  `fork/exec …/usr/bin/wanctl: permission denied` — rule 2 above. It now invokes
  the linker explicitly, the way Termux's own interceptor does, shaping `argv`
  so the child parses its flags correctly.

- **Device names fell back to `wanctl-agent`.** Termux ships its own `getprop`
  and puts `$PREFIX/bin` ahead of `/system/bin` on `PATH`, so resolving it by
  name found a binary this process may not exec. Every Termux device therefore
  collided on one generic name — the exact failure the property lookup exists to
  prevent. It is now read from `/system/bin/getprop`.

The general rule, now applied everywhere: **anything the agent execs on Android
must be named by its system absolute path, never resolved through `PATH`.** The
session shell already followed it; `getprop` did not.

## Upgrading

On a v0.1.7 Termux install `wanctl update` cannot be typed as `wanctl update`
(that is the first bug), and running it as root is dangerous (the second). Re-run
the one-line installer instead:

```sh
curl -fsSL https://relay.example.com/install.sh | sh
```

## Verified

On a vivo PA2353 (Android 13) through the published one-line installer, not a
locally built binary: bare / relative / absolute invocation, a subcommand with
flags, `wanctl start` detaching a working agent, `wanctl update` naming the
right file, and the device registering as `pa2353`.
