WebFetch quick reference

Every step is a GET with your URL-reading tool: authorization, tool calls and results. The human acts twice — once to approve device access, once to approve pairing.

Step 1 of 2: device access

Start at the protocol entry below and follow its procedure. It returns approval_url and continuation_prompt: show both to the human, ask them to approve a duration longer than the task needs, then read status_url until status is approved. Keep the full status_url and the exec call_url_template in your reply so a later turn can continue.

Call a tool

Syntax only. CALL_ENDPOINT, the templates and the allowed target values all come from the approved status response; never invent one or fetch an unfilled template.

GET CALL_ENDPOINT?rid={rid}&tool=exec&target={target}&command={command}

URL-encode each value once: target is the full namespace/device_id with its slash as %2F, and the command ls -la becomes command=ls%20-la. rid is a new operation ID of 1–64 letters, digits, hyphens or underscores — a new one per new operation, the same one to retry that operation.

toolRequired values besides rid and target
execcommand, optional cwd and timeout_seconds (1–14400, default 300)
read_textpath, optional offset (1-based line, default 1) and limit (lines, default 2000)
edit_textpath, old, new, optional all and expected_sha256
write_textpath, content (content= explicitly writes an empty file)

Looking at a file is read_text, not exec with cat: it returns the lines you asked for plus total_lines and the whole file's sha256, and you page on with offset=last_line+1. Changing a file that already exists is edit_text, not write_text: it replaces one exact string in place and keeps the rest of the file byte for byte, while write_text overwrites everything. Pass the sha256 read_text gave you as expected_sha256 so a concurrent change cannot be lost. A refused edit does not replace the file and says why — fix old, new or expected_sha256 and resubmit under a new rid.

Read the actual result

The call returns job_id and result_url. Read result_url, then follow next_url while it runs, waiting poll_after_seconds between reads. A build or render legitimately runs for minutes, up to deadline_at. done carries the result: for exec report stdout, stderr and exit_code. failed is an error. unknown means it may have run — never repeat it automatically; ask the human to check the device. A page that loads is not a result: check status and http_status. Add format=json for strict HTTP status codes.

Step 2 of 2: pairing

Approved device access is not pairing. If a result carries error_code pairing_required, it also carries execution_started: false — nothing ran. Show the human pairing_url and wait until they say they approved it; never fetch that link yourself. Then submit the same operation again under a NEW rid. The refused job stays failed. Device permission rules still apply, and if the grant expires or is revoked, stop and report it.
